# WebSocket API Documentation: Trading Control Panel

## 1. Overview

This document defines the WebSocket communication protocol between the various frontend panels (`single.html`, `multi.html`, `micro.html`) and the backend server for managing and monitoring trading accounts.

*   **Connection URL:** `ws://localhost:9999` (Configurable)
*   **Protocol:** JSON messages over WebSocket
*   **Authentication:** None (Designed for local testing)

## 2. Message Format

All communication uses JSON objects. There are three main types of messages:

1.  **Requests (Client -> Server):** Initiated by the client to request data or trigger an action.
2.  **Responses (Server -> Client):** Sent by the server in direct reply to a client Request.
3.  **Pushes (Server -> Client):** Sent by the server asynchronously to update the client (e.g., account changes, logs).

### 2.1. Request Format (Client -> Server)

```json
{
  "requestId": "unique-string-identifier", // REQUIRED: UUID generated by client
  "command": "command_name",              // REQUIRED: The action or data request
  "payload": { ... }                      // OPTIONAL: Command-specific data
}
```

### 2.2. Response Format (Server -> Client)

Sent in reply to a client Request. Must include the original `requestId`.

**Success Response:**

```json
{
  "requestId": "unique-string-identifier", // REQUIRED: Matches the client request ID
  "status": "ok",                         // REQUIRED: Indicates success
  "data": { ... }                         // OPTIONAL: Data requested by the client or confirmation message
}
```

**Error Response:**

```json
{
  "requestId": "unique-string-identifier", // REQUIRED: Matches the client request ID
  "status": "error",                      // REQUIRED: Indicates failure
  "error": "Descriptive error message"    // REQUIRED: Reason for failure
}
```

### 2.3. Push Format (Server -> Client)

Sent asynchronously by the server after subscriptions are active or for general updates.

```json
{
  "type": "update_type", // REQUIRED: Type of push notification
  "data": { ... }        // REQUIRED: The actual update data
}
```

## 3. Requests (Client -> Server Commands)

The following commands can be sent from the client to the server.

### `get_account_status`

*   **Purpose:** Requests the current full status of the *single reference* account (details, PNL, positions, orders). The backend determines which account is the reference.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `single.html`, `micro.html` (on initial connect)

### `get_multi_account_status`

*   **Purpose:** Requests the current full status of *all* managed accounts simultaneously.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `multi.html` (on initial connect, manual refresh)

### `get_global_symbols`

*   **Purpose:** Requests the list of tradeable symbols available globally or for the reference account context.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `single.html`, `micro.html` (on initial connect)

### `subscribe_account`

*   **Purpose:** Client subscribes to receive `account_update` pushes whenever the *single reference* account state changes.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `single.html`, `micro.html` (on initial connect)
*   **Note:** Server should automatically send `account_update` pushes after this subscription is acknowledged.

### `subscribe_multi_account`

*   **Purpose:** Client subscribes to receive `multi_account_update` pushes whenever the state of *any* managed account changes.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `multi.html` (on initial connect)
*   **Note:** Server should automatically send `multi_account_update` pushes after this subscription is acknowledged.

### `subscribe_logs`

*   **Purpose:** Client subscribes to receive `log_update` pushes for relevant system events, trade confirmations, errors etc. Logs may be global or filtered by context depending on the backend implementation.
*   **Payload:** `{}` (Empty or omitted)
*   **Used By Client(s):** `single.html`, `multi.html`, `micro.html` (on initial connect)
*   **Note:** Server should automatically send `log_update` pushes after this subscription is acknowledged.

### `trade`

*   **Purpose:** Requests placing a trade order on the reference account. The backend is responsible for potentially scaling and copying this trade to other managed accounts based on its internal logic.
*   **Payload:**
    ```json
    {
      "symbol": "EURUSD",          // REQUIRED: Symbol to trade
      "direction": "buy" | "sell", // REQUIRED: Trade direction
      "ordertype": "market",       // REQUIRED: Currently only market supported by UI
      "qty": 1.5,                  // REQUIRED: Base quantity (backend scales)
      "sl_pips": 0                 // OPTIONAL: Stop loss in pips (UI sends 0)
      // Add other parameters like TP, magic numbers if needed by backend
    }
    ```
*   **Used By Client(s):** `single.html`, `micro.html`

### `flatten`

*   **Purpose:** Requests closing positions and potentially cancelling orders. Applies to the reference account and is expected to be scaled/copied to other accounts by the backend.
*   **Payload:**
    *   `{ "instrument": "EURUSD" }`: Flattens only the specified symbol.
    *   `{}` (Empty or omitted): Flattens the *entire* portfolio (all symbols).
*   **Used By Client(s):** `single.html`, `micro.html`

### `cancel`

*   **Purpose:** Requests cancelling pending orders on the reference account. Expected to be scaled/copied by the backend.
*   **Payload:**
    *   `{ "instrument": "EURUSD" }`: Cancels pending orders for the specified symbol only (*optional, UI currently doesn't use this specific payload*).
    *   `{}` (Empty or omitted): Cancels *all* pending orders.
*   **Used By Client(s):** `single.html`

## 4. Responses (Server -> Client Payloads)

Examples of the `data` field within a success (`status: "ok"`) response.

*   **For `get_account_status`:**
    ```json
    {
      "data": {
        "account": { /* See Account Data Structure below */ }
      }
    }
    ```
*   **For `get_multi_account_status`:**
    ```json
    {
      "data": {
        "accounts": [
          { /* Account Data Structure for account 1 */ },
          { /* Account Data Structure for account 2 */ },
          ...
        ]
      }
    }
    ```
*   **For `get_global_symbols`:**
    ```json
    {
      "data": {
        "symbols": ["EURUSD", "GBPUSD", "USDJPY", ...]
      }
    }
    ```
*   **For `trade`, `flatten`, `cancel` (and potentially `subscribe_` commands if explicit confirmation is desired):**
    ```json
    {
      "data": {
          "message": "Order submitted successfully." // Optional confirmation message
      }
    }
    ```
    *(An empty `data: {}` object is also acceptable on success for actions)*

## 5. Pushes (Server -> Client Messages)

Messages sent asynchronously by the server.

### `account_update`

*   **Purpose:** Sent (after `subscribe_account`) when the *single reference* account's status, PNL, positions, or orders change.
*   **Payload (`data`):** Contains the *complete, updated* state of the reference account.
    ```json
    {
      "type": "account_update",
      "data": {
        "account": { /* See Account Data Structure below */ }
      }
    }
    ```
*   **Listened For By Client(s):** `single.html`, `micro.html`

### `multi_account_update`

*   **Purpose:** Sent (after `subscribe_multi_account`) whenever the data for *one or more* managed accounts changes. Contains the *complete, current state* of *all* accounts.
*   **Payload (`data`):**
    ```json
    {
      "type": "multi_account_update",
      "data": {
        "accounts": [
          { /* Complete Account Data Structure for account 1 */ },
          { /* Complete Account Data Structure for account 2 */ },
          ...
        ]
      }
    }
    ```
*   **Listened For By Client(s):** `multi.html`

### `log_update`

*   **Purpose:** Sent (after `subscribe_logs`) to provide status messages, trade confirmations, errors, etc. Can be global or context-specific.
*   **Payload (`data`):**
    ```json
    {
        "type": "log_update",
        "data": {
          "message": "EURUSD BUY order filled at 1.0850",
          "source": "TraderBackend" // OPTIONAL: Source identifier
        }
    }
    ```
*   **Listened For By Client(s):** `single.html`, `multi.html`, `micro.html`

### `symbols_update`

*   **Purpose:** (Optional) Sent if the list of available symbols changes dynamically after the initial connection.
*   **Payload (`data`):**
    ```json
     {
         "type": "symbols_update",
         "data": {
           "symbols": ["EURUSD", "XAUUSD", "US30", ...]
         }
     }
    ```
*   **Listened For By Client(s):** `single.html`, `micro.html` (Potentially `multi.html` if it displayed symbols)

## 6. Data Structures

Common data object structures used within responses and pushes.

### 6.1. Account Data Structure (`account`)

Represents the state of a single trading account.

```json
{
  "id": "456676655",             // REQUIRED: Unique Account Identifier (string)
  "type": "MetaTrader5",          // OPTIONAL: Type of the backend connection (e.g., MT5, IBKR, NT)
  "displayName": "Reference Oanda 10K", // OPTIONAL: User-friendly name
  "status": "Connected" | "Connecting" | "Disconnected" | "Error", // REQUIRED: Connection status
  "error": null | "Connection failed: Timeout", // OPTIONAL: Error message if status is 'Error'
  "realizedPNL": -10.20,          // OPTIONAL: Account realized PNL (number)
  "unrealizedPNL": 25.80,         // OPTIONAL: Account unrealized PNL (number)
  "positions": [ /* Array of Position Objects, see below */ ], // REQUIRED (can be empty array)
  "orders": [ /* Array of Order Objects, see below */ ],     // REQUIRED (can be empty array)
  "lastUpdated": "2023-10-27T10:30:00Z" // OPTIONAL: ISO 8601 timestamp of data generation
}
```

### 6.2. Position Object

Represents an open position within an account.

```json
{
  "symbol": "EURUSD",         // REQUIRED: Broker-specific symbol (string)
  "displaySymbol": "EURUSD",  // OPTIONAL: Symbol to display in UI (might differ)
  "direction": "SELL" | "BUY",// REQUIRED: Direction of the position
  "quantity": -0.05,          // REQUIRED: Position size (negative for SELL, positive for BUY) (number)
  "avgPrice": 1.0850,         // REQUIRED: Average entry price (number)
  "pnl": 25.80                // OPTIONAL: Current unrealized PNL for this position (number)
}
```

### 6.3. Order Object

Represents a pending order within an account.

```json
{
  "symbol": "GBPUSD",         // REQUIRED: Broker-specific symbol (string)
  "displaySymbol": "GBPUSD",  // OPTIONAL: Symbol to display in UI
  "direction": "BUY" | "SELL",// REQUIRED: Order direction
  "quantity": 0.1,            // REQUIRED: Order quantity (number)
  "orderType": "limit" | "stop" | "market", // REQUIRED: Type of pending order
  "price": 1.2500             // REQUIRED: Price for limit/stop (null/0 for market) (number)
  // Add other relevant fields like order ID, status if available/needed
}
```

## 7. Workflow Examples

### 7.1. Single Account Interaction (`single.html` / `micro.html`)

1.  **Connect:** Client opens WebSocket connection.
2.  **Server:** Accepts connection.
3.  **Client `onopen`:**
    *   Sends `{"requestId": "req-1", "command": "get_account_status", "payload": {}}`
    *   Sends `{"requestId": "req-2", "command": "get_global_symbols", "payload": {}}`
    *   Sends `{"requestId": "req-3", "command": "subscribe_account", "payload": {}}`
    *   Sends `{"requestId": "req-4", "command": "subscribe_logs", "payload": {}}`
4.  **Server:**
    *   Processes `req-1`. Sends `{"requestId": "req-1", "status": "ok", "data": {"account": {...}}}`.
    *   Processes `req-2`. Sends `{"requestId": "req-2", "status": "ok", "data": {"symbols": [...]}}`.
    *   Processes `req-3`. Acknowledges internally. Sends `{"requestId": "req-3", "status": "ok", "data": {}}`.
    *   Processes `req-4`. Acknowledges internally. Sends `{"requestId": "req-4", "status": "ok", "data": {}}`.
5.  **Client:** Receives responses, updates UI (account details, PNL, symbols).
6.  **User Action:** Clicks "Buy EURUSD" on `single.html` or `micro.html`.
7.  **Client:** Sends `{"requestId": "req-5", "command": "trade", "payload": {"symbol": "EURUSD", "direction": "buy", ...}}`.
8.  **Server:** Processes trade (including scaling/copying logic). Sends `{"requestId": "req-5", "status": "ok", "data": {"message": "Buy order placed"}}`.
9.  **Client:** Receives response, shows success alert/status.
10. **Backend Event:** Trade fills, reference account state changes.
11. **Server:**
    *   Sends `{"type": "log_update", "data": {"message": "Reference EURUSD BUY filled"}}` (due to log subscription).
    *   Sends `{"type": "account_update", "data": {"account": { /* new reference account state */ }}}` (due to account subscription).
12. **Client:** Receives pushes, adds log message (`single.html`/`micro.html`), updates account details/PNL (`single.html`/`micro.html`).

### 7.2. Multi-Account Overview (`multi.html`)

1.  **Connect:** Client (`multi.html`) opens WebSocket connection.
2.  **Server:** Accepts connection.
3.  **Client `onopen`:**
    *   Sends `{"requestId": "mreq-1", "command": "get_multi_account_status", "payload": {}}`
    *   Sends `{"requestId": "mreq-2", "command": "subscribe_multi_account", "payload": {}}`
    *   Sends `{"requestId": "mreq-3", "command": "subscribe_logs", "payload": {}}`
4.  **Server:**
    *   Processes `mreq-1`. Fetches all accounts. Sends `{"requestId": "mreq-1", "status": "ok", "data": {"accounts": [{...}, {...}]}}`.
    *   Processes `mreq-2`. Acknowledges internally. Sends `{"requestId": "mreq-2", "status": "ok", "data": {}}`.
    *   Processes `mreq-3`. Acknowledges internally. Sends `{"requestId": "mreq-3", "status": "ok", "data": {}}`.
5.  **Client:** Receives response for `mreq-1`, renders all account cards.
6.  **Backend Event:** Account 'XYZ' disconnects.
7.  **Server:** Sends `{"type": "multi_account_update", "data": {"accounts": [{...account1_unchanged...}, {...accountXYZ_updated_status...}]}}` (due to `subscribe_multi_account`).
8.  **Client:** Receives `multi_account_update`, re-renders cards, showing Account 'XYZ' as disconnected.
9.  **User Action:** Clicks "Refresh Now".
10. **Client:** Sends `{"requestId": "mreq-4", "command": "get_multi_account_status", "payload": {}}`.
11. **Server:** Processes `mreq-4`. Fetches current state again. Sends `{"requestId": "mreq-4", "status": "ok", "data": {"accounts": [{...}, {...}]}}`.
12. **Client:** Receives response for `mreq-4`, re-renders cards (likely showing the same state as the last push).
